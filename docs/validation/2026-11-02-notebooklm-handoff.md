Это итог работ и журнал подтверждённых наблюдений, а не утверждение, что все проблемы NotebookLM решены. Эксперименты выполнялись в предыдущих этапах сессии; при завершении состояние роутера прочитано без изменения настроек. ## Постоянные журналы и админка

Журналы находятся в */etc/vpn-guardian/diagnostics/*: *events.log*, *health.jsonl*, *probes.jsonl* и их ротации. Служба *vpn-guardian-diagnostics* работает независимо от маршрутизации. Сохранение записей при перезапуске службы проверялось ранее; отдельный полный reboot ради этой доработки не выполнялся.

Каждый поток ограничен 2 МиБ плюс три архивные части, суммарно около 24 МиБ. В админке QUIC-события доступны после авторизации. Счётчик отклонённых UDP/443-пакетов отражает работу режима совместимости, а не количество ошибок протокола. Отсутствие записи об ошибке на роутере не исключает сбой браузера или мобильного приложения.

Служебные 5/5 проверки не означают успешного отображения всех сайтов: HTTP 401 от служебного endpoint и HTTP 403 защитной страницы не равнозначны работоспособности пользовательского интерфейса.

## QUIC: подтверждено и не подтверждено

На исходном Xray 25.1.30 ранее воспроизводилось различие для одного веб-домена: HTTP/2 возвращал 200, принудительный HTTP/3 — 404. Проверка соединений на роутере показала прямой UDP-выход из Xray при нераспознанном QUIC. Это отдельный обнаруженный дефект классификации, не доказательство причины всех белых экранов.

После обновления отдельного Xray до 26.10.21 в повторных тестах новые прямые UDP-соединения не наблюдались, однако принудительный HTTP/3 всё ещё завершался ошибками. Полное исправление QUIC обновлением не подтверждено. Откат на старую версию также не дал доказанного решения всех сценариев.

Поэтому реализован *tcp-fallback*: внешний UDP/443 клиентов отклоняется немедленно, браузеры с поддержкой возврата к TCP могут использовать HTTP/2 или HTTP/1.1. Это обход нестабильного транспорта, не исправление QUIC-sniffer. Приложениям, которым необходим UDP/443 без альтернативы, режим может мешать.

Режим не меняет VPN-транспорт самого роутера и не блокирует остальные UDP-порты. Внешний IPv6 и неподдерживаемые прокси протоколы в Full VPN блокируются от обхода VPN, а не туннелируются. Локальная сеть, DNAT-исключения и служебный трафик роутера имеют отдельную семантику, описанную в реализации.

## DNS и полнота маршрутов

Для DIRECT сохранено использование штатных системных/WAN DNS роутера, без хардкода DNS вышестоящего устройства. В Full VPN действует отдельная runtime-политика для всех внешних DNS-запросов; исходные выборочные настройки сохранены для возврата в Auto.

При реализации полного режима обнаружено, что обычный catch-all *server=/#/* мог участвовать в общем пуле вместе с сохранёнными WAN upstream. Исправление использует явный regex-selector перед этим пулом, сохраняя приоритет локальных зон:

~~~text
server=/regex:^.*$/127.0.0.1#20176
~~~

Это поведение относится к используемому Guardian-варианту dnsmasq с поддержкой regex-server. Не переносить вывод на произвольную сборку dnsmasq без проверки. В runtime-тесте новые внешние запросы увеличивали VPN-счётчик DNS; локальное имя роутера продолжало разрешаться локально.

Для диагностической проверки NotebookLM в группу Google AI на стенде добавлены точные правила *full* для следующих доменов:

~~~text
www.gstatic.com
ogs.google.com
ogads-pa.clients6.google.com
lh3.googleusercontent.com
fonts.gstatic.com
fonts.googleapis.com
ssl.gstatic.com
www.googletagmanager.com
region1.analytics.google.com
play.google.com
~~~

Они дополняют существующие *domain:notebook.google*, *domain:notebook.google.com*, *full:accounts.google.com* и *geosite:google-gemini*. Эти общие Google-домены не специфичны для NotebookLM; их добавление не устранило региональный отказ. Полный охват также не помог на проверенном обычном VPN-выходе. Правила не удалялись автоматически и не объявлены обязательным набором для всех пользователей.

## NotebookLM: веб-версия и приложение — разные проверки

| Сценарий | Основание | Наблюдение |
|---|---|---|
| Веб-версия через обычные VPN-ноды, в том числе при Full VPN | Проверки на стенде | Редирект приложения с *location=unsupported*; лендинг может отвечать 200. |
| Веб-версия через AI-ноду того же провайдера | Повторные проверки backend и Mac | 200 с кодом веб-приложения, без регионального редиректа. |
| AI-нода: передача домена против фиксированного IPv4 | Изолированный тест с отключённым sniffing | Оба варианта дали успешные ответы веб-приложения; простое различие формы назначения отказ не воспроизвело. |
| Телефон, мобильная сеть, Incy, AI-нода, прямое открытие веб-адреса | Сообщение пользователя | Веб-версия работает. |
| Тот же телефон, мобильное приложение через Incy | Сообщение пользователя | Приложение загружается, затем сообщает о неподдерживаемом регионе. |
| То же мобильное приложение через WireGuard | Сообщение пользователя | Работает. |
| Incy с отключённым профилем маршрутизации | Сообщение пользователя | Проблема приложения сохранилась. |

Ключевой адрес для проверки веб-приложения: <https://notebook.google.com/>. *notebook.google* — лендинг; его HTTP 200 не является проверкой доступа к приложению. Редирект с уже имеющимся *location=unsupported* не доказывает новую региональную проверку на изменившемся VPN-маршруте.

При одной и той же активной AI-ноде независимые контрольные сервисы видели разные выходные адреса. Это согласуется с пулом выходов или серверной маршрутизацией провайдера, но точная схема не установлена. Выход, видимый ipify, не является измерением адреса, который увидел конкретный запрос NotebookLM. Диагностическая подсеть из Google DNS также не является точным адресом соединения с приложением.

Утечка регионально отклонённого запроса мобильного приложения на домашний/мобильный IP не доказана. Различие VLESS против WireGuard не изолировано: одновременно меняются клиент и удалённый выход. Гипотеза о влиянии профиля Incy не подтвердилась отключением его тумблера, но полный итоговый конфиг Incy не исследован.

Неудачный ранний запуск параллельных изолированных прокси завершился *curl exit 7*. Его результаты не являются сравнением доступности Google через соответствующие ноды и не должны использоваться как доказательство блокировки провайдером.

## Прочие отдельные наблюдения

В основном профиле Яндекс Браузера обнаружен PAC расширения Browsec: *ya.ru* и *yandex.ru* направлялись через три HTTPS-прокси без DIRECT fallback. Эти прокси не отвечали напрямую, но соединялись через VPN. Это объясняло наблюдавшиеся тайм-ауты Яндекса, но не белые экраны других сайтов, для которых PAC возвращал DIRECT.

Одна запись о сбое Яндекс Браузера относилась к автоматизированному тестовому процессу, а не к основной пользовательской сессии. Не считать её доказательством пользовательского падения. Большое число сохранённых браузером неудачных QUIC alternative services — зацепка, но без сопоставимого периода нагрузки не доказательство причинной связи.

В исследованном интервале постоянных логов не было выявлено падений основных процессов Guardian; встречались отдельные EOF при чтении DNS-ответов. Связь этих EOF с белыми экранами не установлена. Успешные процессные и сетевые проверки не исключают проблем отдельных соединений.

## Что осталось сделать при возобновлении

Первый незавершённый контрольный эксперимент: открыть именно мобильное приложение через Wi-Fi GL-MT с выбранной AI-нодой и Full VPN, отключив Incy, WireGuard и мобильные данные на телефоне. Сравнить с тем же приложением через Incy и WireGuard. Сейчас не утверждается, что мобильное приложение работает через AI-ноду Guardian.

Далее исследовать фактические адреса и ошибки мобильного клиента и итоговую конфигурацию Incy. Кандидаты из предыдущего этапа исследования: *notebooklm-pa.googleapis.com* и *notebooklm.googleapis.com*. Использование именно этих адресов приложением пользователя не подтверждено его журналом; успешный HTTP-запрос к корню API не заменяет авторизованный запрос приложения. Новые правила для них при завершении не добавлялись.

При новом HAR включать запись до перехода к приложению, Preserve log и отключение кэша. Нужно сохранять исходный ответ, впервые добавляющий *location=unsupported*, а не только последующий лендинг. HTTP/3, указанный у записи из дискового кэша, сам по себе не доказывает новое UDP-соединение.

Будущая отдельная возможность Guardian: выбирать специальный VPN-backend для группы Google AI. Сейчас группы — метаданные, а не выбор индивидуальных выходов. Доработка не реализована и не обещана в рамках завершённой сессии.

## Границы сохранения

В репозитории сохраняются код, тесты, описание реализации и этот обезличенный итог. Не публикуются HAR с авторизацией, cookies, токены управления, UUID и ключи VPN, полные конфиги подписок, приватные БД и сырые пользовательские сетевые журналы. Постоянные диагностические журналы остаются на роутере. Временные конфигурации с секретами не переносятся из */tmp* в Git.

Команды повторной проверки проекта, без изменения рабочих настроек:

~~~sh
go test ./... -count=1
go vet ./...
go test -race ./internal/api ./internal/config ./internal/stack ./internal/dnsproxy ./internal/diagnostics -count=1
npm --prefix webui run test:unit
npm --prefix webui run check
~~~
