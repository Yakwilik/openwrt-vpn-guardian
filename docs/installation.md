# Установка и диагностика

## Совместимость

Пакеты собираются для **OpenWrt 24.10.4** с менеджером пакетов *opkg*, на закреплённых SDK. Совместимость не определяется только CPU: должны совпадать ABI системных библиотек, прошивка и зависимости ядра. Используйте feeds от установленной прошивки: из них устанавливаются Xray, nftables, iproute2, CA-сертификаты, geodata и модуль TPROXY.

| Архитектура пакета | SDK target | Платформа |
|---|---|---|
| aarch64_cortex-a53 | mediatek/filogic | ARM64 |
| arm_cortex-a7_neon-vfpv4 | ipq40xx/generic | ARMv7 |
| x86_64 | x86/64 | x86-64 |

Архитектуры, которые принимает роутер:

~~~sh
opkg print-architecture
~~~

Выберите пакеты с соответствующей архитектурой (в dnsmasq перед суффиксом *.openwrt* или *.glinet*). Пакеты IPK не предназначены для прошивок с apk; MIPS пока не поддерживается.

## Комплект пакетов

В [Releases](https://github.com/Yakwilik/openwrt-vpn-guardian/releases) в разделе **Assets** опубликованы:

- *vpn-guardian* — управляющий пакет с веб-интерфейсом;
- *v2raya* 2.5.8 — совместимый backend с собственным core;
- *dnsmasq-full* 2.90-r5.1 — модифицированный DNS/DHCP с regex-селекторами и подтверждением безопасного обновления правил. Выберите **один** вариант: *.openwrt.ipk* (обычный OpenWrt) или *.glinet.ipk* (прошивка GL.iNet с фирменным SO_MARK и init-скриптом).

Каждый IPK содержит архитектуру в имени; дополнительные суффиксы *.openwrt* и *.glinet* у DNS-пакета не меняют его внутреннее имя *dnsmasq-full*. Для каждого файла опубликованы SHA-256 и сведения о сборке, а также исходные архивы dnsmasq и v2rayA. Обычный v2rayA из feed OpenWrt 24.10 содержит старый формат базы и не подходит.

**Перед заменой DNS:** сохраните */etc/config/dhcp*, войдите по SSH непосредственно на IP роутера, убедитесь, что доступна локальная резервная точка входа. Установка dnsmasq-full заменяет системный DNS/DHCP и может прервать подключение клиентов. Не используйте отдалённое управление, зависящее исключительно от DNS обновляемого роутера.

~~~sh
cp /etc/config/dhcp /root/dhcp.before-vpn-guardian
opkg update
~~~

Скопируйте **три подходящих IPK** одного релиза в */tmp*. На **стандартном OpenWrt**:

~~~sh
opkg install /tmp/dnsmasq-full_*.openwrt.ipk /tmp/v2raya_*.ipk /tmp/vpn-guardian_*.ipk
vpn-guardian init
~~~

На **GL.iNet** с фирменной маркировкой DNS (вариант проверен на GL-MT6000):

~~~sh
opkg install /tmp/dnsmasq-full_*.glinet.ipk /tmp/v2raya_*.ipk /tmp/vpn-guardian_*.ipk
vpn-guardian init
~~~

Если штатный пакет называется *dnsmasq* (не *dnsmasq-full*) и *opkg* сообщает конфликт пакетов, сначала сохраните конфигурацию и удалите старый пакет командой *opkg remove dnsmasq*, затем повторите установку всех трёх IPK. Для установки зависимостей должны быть настроены feeds **именно установленной прошивки**; несовместимый системный ABI или отсутствующий модуль TPROXY — причина остановить установку, а не принудительно игнорировать зависимости.

Проверьте, что DNS-патч присутствует:

~~~sh
dnsmasq --version
~~~

Строка *Compile time options* должна содержать *regex-server* и *regex-server-ack*. Для GL.iNet в *dnsmasq --help* также должен быть параметр *--mark*. На обычном OpenWrt этот параметр не требуется.


Установка пакета сама по себе не включает перехват LAN. Настройка и активация выполняются командой *init* из интерактивной SSH-сессии с правами root. Отдельная установка Go, сборка бинарника и копирование init-скриптов на роутер не требуются.

## Что делает мастер

Мастер проверяет версии и запуск зависимостей, доступ к nftables, policy routing, UCI, ubus, сетевым устройствам, сертификатам и geodata. Затем определяет LAN/WAN, предлагает выбрать разрешённые протоколы и запрашивает подписки. Уже существующие правила маршрутизации сохраняются.

Для новой v2rayA мастер запросит аккаунт. Пароль вводится без отображения и не сохраняется в manifests Guardian. Подписки передаются в v2rayA и не раскрываются в read-only API. v2rayA переводится в backend-only mode с SOCKS на loopback; её собственный transparent proxy остаётся выключенным.

До включения Guardian проверяются оба manifests, конфигурации Xray, синтаксис nftables, доступ к базе и API v2rayA, наличие разрешённых нод и соединение через выбранную ноду. Если активация не проходит, применяется rollback. Установочный сценарий не снимает существующую VPN-only interception при ошибках проверки.

После успешной активации сервисы включаются для автозапуска. LAN DNS принимает dnsmasq на порту 53; Guardian на 127.0.0.1:20176 обслуживает выбранные защищённые домены. Обычный внешний DNS и локальные OpenWrt/DHCP-имена продолжат разрешаться при остановке Guardian. Для внешних запросов в веб-панели доступны System, Custom и Xray; по умолчанию Custom применяется только к доменам из VPN routing rules. Отдельный переключатель распространяет его на весь внешний DNS. VPN-only запрещает прямой fallback, Fail-open разрешает DNS fallback и при подтверждённом отказе backend переводит proxy-класс в direct, Direct сразу использует системные upstream-ы. Исходные системные resolver-ы (приоритетно) и текущий WAN DNS (дополнительный fallback) отдельно обеспечивают bootstrap роутера без зависимости от Guardian. Management/WAN-сеть не должна использовать GL-MT как DNS; локальные имена на upstream-роутере задаются его собственными записями. Панель доступна на LAN-адресе, порт 20175; nginx для этого не требуется.

## Если проверка не проходит

Исправьте причину из сообщения и повторите *vpn-guardian init*. Мастер не запускает бесконечные попытки настройки в фоне. Если отсутствует только один из двух существующих manifests, восстановите его из резервной копии: потерянные правила не заменяются стандартными.

Проверка готовой конфигурации без изменений:

~~~sh
vpn-guardian bootstrap --dry-run
~~~

Состояние и встроенная проверка работающего стека:

~~~sh
vpn-guardian status
vpn-guardian selftest
~~~

Для автоматизации можно использовать *vpn-guardian bootstrap --non-interactive*. Команда проверяет сохранённые настройки и зависимости, но не читает stdin. При недостающих данных она завершается с ошибкой; завершите настройку через интерактивный *init*.

## Обновление

Установите новый комплект IPK и выполните *vpn-guardian bootstrap* из SSH. Обновление пакетов сохраняет manifests и включённую interception; bootstrap проверяет конфигурацию и применяет новый runtime. Для изменения списка разрешённых протоколов используйте *vpn-guardian init*.

## Сборка для разработки

На компьютере с Go 1.23 или новее:

~~~sh
go test ./...
go vet ./...
go test -race ./...
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -trimpath -o dist/vpn-guardian-linux-arm64 ./cmd/vpn-guardian
~~~

Для воспроизводимой пакетной сборки используются официальный OpenWrt SDK, закреплённые ревизии feeds и точный commit проекта. Рецепты находятся в *package/*, сборочный скрипт — в [scripts/package-openwrt.sh](../scripts/package-openwrt.sh).

## Миграция на native split DNS

После обновления бинарника активный стек можно перевести командой *vpn-guardian dns-install*. Она проверяет конфигурацию, сохраняет параметры dnsmasq, поднимает loopback upstream, обновляет DNS-интеграцию, собственную nftables-таблицу и необходимые policy variants. vpn-front обновляется только при изменении сгенерированной конфигурации, в том числе для сохранения выбранного клиентом IP. v2rayA и management firewall не пересоздаются; vpn-policy перезапускается только если его сгенерированная схема действительно изменилась. Первичная миграция перезапускает dnsmasq; последующие изменения из админки в совместимой сборке используют подтверждаемую native загрузку правил и очистку кэша без перезапуска DNS/DHCP. При обновлении бинарника также перезапускаются работающие API и collector, чтобы они использовали новую реализацию применения и проверки DNS.

Для поддерживаемого релизного комплекта используйте поставляемый с ним *dnsmasq-full* из [package/dnsmasq-guardian](../package/dnsmasq-guardian/README.md), так как штатный dnsmasq не поддерживает все regex-селекторы. Она добавляет native regex selectors и сохраняет штатные функции DHCP/DNS. При отсутствии нужной возможности миграция отклоняется; общий DNS не перенаправляется в Guardian как обходной путь.

Миграция требует единственного однозначно определяемого экземпляра dnsmasq на порту 53. Внешние доменные override-server правила, способные обойти DNS policy, отклоняются; внутренние split-horizon resolver-ы остаются у dnsmasq. При удалении пакета сначала восстанавливается исходная DNS-интеграция. Проверки с остановкой процессов выполняются только через независимое подключение управления.
